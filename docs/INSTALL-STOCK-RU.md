# Со стоковой JDCloud на нашу OpenWrt: понятная инструкция

**Устройство: JDCloud RE-CS-06 / «赵云» / BE6500.**
Наша система — экспериментальная сборка на основе LEDE/OpenWrt, не официальный
релиз OpenWrt и не QWRT.

> **Статус инструкции:** проверенный маршрут миграции и подготовка для владельца,
> но пока **не готовая инструкция «скачал и прошил любой сток»**. На втором
> устройстве r9 установлена, настройки восстановились автоматически, вход по
> SSH и две перезагрузки по сети проверены. Холодное включение и остальные
> физические порты ещё не приняты. Универсальный установщик со стока не выпущен,
> а полный локальный r9 не опубликован как готовый Wi-Fi-образ.
>
> **До этапа 6 можно готовиться по этой инструкции. На этапе 6 нужен проверенный
> установочный комплект именно для вашей разметки и загрузчика. Если его нет —
> остановитесь, не заменяйте его командами из случайного видео.** Это ограничение
> написано специально, чтобы инструкция не превращала исправный роутер в кирпич.

## Коротко: что мы делаем

1. Оставляем роутер без интернета и подключаем компьютер кабелем в LAN.
2. Проверяем модель и версию стока, получаем локальную консоль.
3. Сохраняем **собственные** резервные копии этого устройства на два накопителя.
4. Проверяем разметку, загрузчик и выбранный образ.
5. Готовим личный пароль, ключ доступа и настройки первого запуска.
6. Записываем систему в **неиспользуемую пару** разделов и только затем выбираем её
   для загрузки. Работающую стоковую пару сохраняем.
7. Проверяем вход по сети, сохранение настроек и повторную загрузку.

**Менять U-Boot, заливать чужой `factory.bin` или переразмечать накопитель для
этого не требуется. UART в исправленном процессе не используется как обязательный
способ настройки. Но авария во время записи всё ещё может потребовать UART.**

## 1. Что приготовить

- Именно **RE-CS-06**. Похожая коробка или название «BE6500» не подтверждают модель.
- Компьютер, Ethernet-кабель и стабильное питание роутера.
- Отдельный накопитель для второй копии бэкапа. Два файла на одном SSD — не две
  независимые копии.
- Достаточно свободного места. eMMC проверенного устройства — около **116,5 ГиБ**.
  Сжатый бэкап может быть существенно меньше, но гарантировать размер заранее
  нельзя. Для несжатого образа нужно не менее 125 057 368 064 байт плюс запас.
- Терминал и инструменты резервного копирования. Команды ниже относятся к Linux;
  сетевые команды Linux нельзя буквально вставлять в PowerShell. WSL тоже требует
  отдельной проверки, к какому интерфейсу он действительно подключается.
- Проверенный комплект нашей сборки с исправлениями r9: образ, контрольные суммы,
  результаты проверки и подходящий способ установки. **Надпись `.bin` сама по себе
  не говорит, куда этот файл можно загружать.**

### Какие файлы не перепутать

| Файл | Для чего он нужен | Куда нельзя отправлять вслепую |
| --- | --- | --- |
| `…squashfs-sysupgrade.bin` | Обновление уже работающей нашей системы; также источник отдельных payload для проверенного установщика | В стоковую кнопку обновления JDCloud |
| `…squashfs-factory.bin` | Контейнер определённого формата установки | В раздел `factory` и в неизвестное recovery |
| `…initramfs-uImage.itb` | Диагностическая загрузка в RAM при отдельно проверенном способе запуска | Вместо постоянного kernel/rootfs |
| `ART`, `factory`, `LICENSE`, образ eMMC | Личные резервные копии конкретного устройства | На другой роутер и в публичный GitHub |
| `config.tgz` | Личный архив первого запуска: пароль, публичный SSH-ключ, свои настройки | В публичную прошивку или публичное вложение |

Старые опубликованные сборки **не становятся r9** из-за нового названия файла.
В них могут отсутствовать исправления Ethernet и восстановления конфигурации.
Полный r9 с радиофайлами пока локальный: [почему](LICENSING.md).
Старый вариант `external-radio` тоже не является готовой заменой r9 с рабочим Wi-Fi.

## 2. Подключить роутер, не потеряв интернет на компьютере

1. **Отключите кабель из WAN роутера.** Интернет ему пока не нужен.
2. Подключите компьютер к одному из LAN. Не соединяйте LAN двух домашних роутеров
   наугад — получите конфликт адресов и DHCP.
3. Дождитесь загрузки. У стока она может быть заметно дольше минуты.
4. Откройте **http://192.168.68.1/**. Это адрес проверенного стокового экземпляра;
   у вашего проверьте адрес шлюза проводного соединения.

Если одновременно нужен интернет по Wi-Fi, проводное соединение **не должно**
подменять основной шлюз и DNS. Особая осторожность нужна, когда оба роутера имеют
адрес `192.168.1.1`: браузер может открыть совсем не тот аппарат.

Для отдельного Linux-компьютера с NetworkManager пример изоляции ниже. Сначала
посмотрите имя интерфейса:

```sh
nmcli device status
```

В примере **замените `enp7s0` на свой Ethernet-интерфейс**. Команда предназначена
для уже активного проводного соединения и **стокового адреса `192.168.68.1`**:

```sh
nmcli --wait 10 device modify enp7s0 \
  ipv4.method manual ipv4.addresses 192.168.68.2/24 \
  ipv4.gateway '' ipv4.never-default yes ipv4.ignore-auto-dns yes \
  ipv4.route-table 110 \
  ipv4.routing-rules 'priority 32031 from 192.168.68.2/32 table 110' \
  ipv6.never-default yes ipv6.ignore-auto-dns yes
```

Проверки:

```sh
ip -4 route get 192.168.68.1 from 192.168.68.2
ip -4 route get 1.1.1.1
curl --interface 192.168.68.2 --noproxy '*' --max-time 5 http://192.168.68.1/
```

Первый маршрут должен идти по Ethernet в таблице `110`, второй — по вашему
обычному интернет-соединению. После потери линка NetworkManager может убрать
временные настройки или правила: **проверяйте маршрут заново**, даже если IP остался.
Не отключайте брандмауэр компьютера целиком ради прошивки.

## 3. Проверить сток и открыть локальную консоль

Описанный доступ проверен на **RE-CS-06, JDCOS-4.5.3.r4530**.
Для другой версии не обещаем, что метод работает. Не обновляйте сток специально
«до последнего»: обновление может изменить загрузчик, разметку или способ доступа.

Если первичная настройка не завершена, задайте уникальный пароль администратора
штатным мастером. Не привязывайте облако, не запускайте обновление и не подключайте
WAN только ради прохождения мастера. Сохраните пароль в менеджере паролей.
На ненастроенном проверенном стоке страница использовала первоначальный
`root/admin`; это **не** пароль нашей системы после установки.

После входа в штатный веб-интерфейс можно выполнить следующий **локальный** код
в консоли разработчика браузера. Это не чтение: он запрашивает заводской флаг
Telnet и запуск службы. Используйте только на своём изолированном роутере.

1. Откройте инструменты разработчика (`F12` или `Ctrl+Shift+J`), вкладку «Console».
2. Убедитесь, что адрес страницы — именно ваш стоковый роутер.
3. Прочитайте код перед выполнением. Он не загружает сторонние скрипты, не содержит
   команд записи прошивки, GPT или U-Boot. Не обходите предупреждение браузера
   о вставке кода, если вы не понимаете, что именно запускаете.

```js
(async () => {
  const session = document.cookie.split('; ')
    .find(x => x.startsWith('sessionid='))?.split('=').slice(1).join('=');
  if (!session) throw new Error('Сначала войдите в штатный веб-интерфейс');
  for (const command of ['factory_hm info telnet 1', 'telnetd']) {
    const response = await fetch('/jdcapi', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        jsonrpc: '2.0', id: 1, method: 'call',
        params: [session, 'jdcapi.static', 'set_port_forward', {
          'on-off': 1, name: 't1', proto: 'TCP',
          'src-dport': '1234;`' + command + '`',
          ipaddr: '192.168.1.100', 'dest-port': '80', edit: 1
        }]
      })
    });
    const result = await response.json();
    console.log('Ответ API, не доказательство запуска:', result.result ?? result.error);
  }
  console.log('Теперь отдельно проверьте подключение Telnet. Не публикуйте cookie/sessionid.');
})();
```

На проверенном аппарате API вернул `status:1`, **но команды выполнились и порт
открылся**. Поэтому сообщение об ошибке не повод бесконечно повторять запросы.
Проверяйте реальное соединение:

```sh
telnet 192.168.68.1 23
```

Логин — `root`, пароль — установленный вами пароль администратора стока.
Telnet передаёт данные без шифрования: только изолированный кабель, без WAN.
Если вход не работает, остановитесь. Не перебирайте пароли и не делайте сброс,
чтобы «помочь» инструкции.

## 4. Сделать резервные копии — до прошивки

В открывшейся консоли пока выполняйте **только чтение**:

```sh
uname -a
cat /proc/cmdline
cat /proc/partitions
cat /proc/mounts
fdisk -l /dev/mmcblk0
cat /sys/block/loop0/loop/backing_file
fw_printenv -n jd_failsafe_counter
```

Сохраните вывод локально. Он может содержать идентификаторы устройства;
не выкладывайте его целиком в комментарии или GitHub.

**Нужны именно скачанные на компьютер файлы, а не скриншоты команд:**

- GPT в начале диска, резервный GPT/конец диска и его геометрия;
- ART, factory, LICENSE — калибровка и индивидуальные данные;
- оба APPSBL, окружение APPSBLENV и оба BOOTCONFIG;
- ранние загрузочные разделы и оба комплекта HLOS/rootfs;
- аппаратные области `mmcblk0boot0` и `mmcblk0boot1`;
- конфигурация/overlay и, предпочтительно, полный образ eMMC.

Бэкап передаётся потоком на компьютер: **не сохраняйте 116 ГиБ в `/tmp` роутера**.
Для каждого файла проверяются размер и SHA256, а не только наличие файла.
Проверку источника и приёмника лучше выполнять по одному и тому же потоку:
живая файловая система между двумя отдельными чтениями может измениться.
Сжатый полный образ нужно полностью прочитать/распаковать при проверке, а не
посмотреть только начало архива. Затем скопировать на второй физический накопитель
и проверить контрольную сумму копии.

**Если готового проверенного инструмента резервного копирования у вас нет — это
первая точка, где нужна помощь.** Наш частный инструмент на втором экземпляре
проверял поток и две физические копии; его нельзя заменить одной непроверенной
командой `nc`, которая оставила на диске файл неизвестной полноты.

Включение Telnet и первичная настройка уже меняют настройки стока. Называйте
полученный бэкап «после настройки/открытия доступа», а не девственным заводским.

## 5. Сверить аппарат и подготовить первый запуск

На проверенном устройстве:

| Что | Значение |
| --- | --- |
| Число разделов GPT | 29 |
| Размер HLOS и HLOS_1 | по 7 МиБ, 14336 секторов |
| Размер rootfs и rootfs_1 | по 122 МиБ, 249856 секторов |
| Работающая до миграции пара | HLOS_1 / rootfs_1 |
| Загрузчик | U-Boot 2016.01, сборка января 2024 |

**Это ориентир для сверки, не команда выбрать те же номера на вашем устройстве.**
Активную пару определяют по фактической загрузке и BOOTCONFIG. Если она отличается,
установочный план должен измениться. При непонятной разметке — остановиться.

У второго экземпляра был повреждён/отсутствовал резервный GPT. Его восстановили
отдельно, не меняя разделы. Это **не обязательный шаг на каждом роутере** и не повод
запускать автоматическое «исправить и расширить всё». Ошибка GPT не означает, что
нужно залить чужой U-Boot или чужой GPT.

Для первого запуска нужен **отдельный личный** архив:

- уникальный пароль root в виде корректной записи `etc/shadow`;
- ваш **публичный** ключ в `etc/dropbear/authorized_keys` — не приватный ключ;
- собственные проводные MAC этого экземпляра и вызов нашего помощника настройки;
- при необходимости контрольный файл, по которому видно, что архив восстановился.

Не берите shadow, host keys, MAC или калибровку первого роутера. Пароль или его хеш
не должен оказаться в GitHub или общем образе. Подготовку `shadow` лучше поручить
установочному инструменту: случайная строка в этом файле может закрыть доступ.

Упаковывать подготовленный несжатый tar следует нашим скриптом на компьютере:

```sh
python3 scripts/make-config-seed.py private-config.tar private-config.tgz
```

Он создаёт новый файл с закрытыми правами доступа и нужным gzip-заголовком.
Он **не создаёт содержимое настроек** и не прошивает роутер.
Обычный архив «который открывается 7-Zip» недостаточен: несовместимый заголовок
стал отдельной причиной неудачи нашей первой установки.

## 6. Запись: не через кнопку обновления стока

> **Стоп-контроль:** без проверенных бэкапов на двух накопителях, совпавшей
> разметки, подходящего образа и готового личного архива дальше не идти.

Не загружайте наш sysupgrade в штатный интерфейс JDCloud. Не используйте для
первого перехода `sysupgrade` из чужой прошивки и не заменяйте установщик
«универсальными» командами записи разделов.

В проверенной миграции установочный инструмент делал следующее:

1. Повторно проверял модель, геометрию, выбранную активную пару и контрольные суммы
   защищённых разделов. Образ и личный архив сначала передавались только в RAM.
2. Записывал squashfs в **неактивный** rootfs, а личный архив — в выровненное место
   будущего overlay. Проверял оба диапазона чтением обратно.
3. Записывал FIT kernel в соответствующий неактивный HLOS и проверял чтением обратно.
4. Снова проверял, что загрузчик, калибровка и рабочая стоковая пара не изменились.
5. **Последним действием** менял только нужный BOOTCONFIG, с корректным возрастом
   записи и выбором новой пары. Другие поля сохранял.
6. Только после успешных проверок разрешал одну контролируемую перезагрузку.

Конкретные команды `dd` и готовый BOOTCONFIG здесь намеренно не приведены:
ошибочный номер раздела или возраст записи может лишить вас и новой системы,
и рабочего пути возврата. **На данный момент публичного универсального инструмента,
который безопасно проделывает эти шаги для произвольного стока, нет.**
Попросите подготовить и проверить комплект для вашего результата шага 4;
не используйте приватные файлы другого владельца вместо установщика.

## 7. Первый вход в нашу систему

После успешной записи и одной перезагрузки адрес меняется:

**http://192.168.76.1/** — LuCI; **SSH `root@192.168.76.1`** — консоль.
Пароль — ваш из личного архива, а не `admin`. Для SSH используется подготовленный
вами ключ. Новая система создаёт свои host keys: не удаляйте вслепую старые ключи
из общего `known_hosts`, а проверьте, что действительно подключились к нужному аппарату.

На компьютере задайте Ethernet-адрес `192.168.76.2/24` без шлюза/DNS. Для приведённого
выше Linux-примера замените проводную настройку:

```sh
nmcli --wait 10 device modify enp7s0 \
  ipv4.method manual ipv4.addresses 192.168.76.2/24 \
  ipv4.gateway '' ipv4.never-default yes ipv4.ignore-auto-dns yes \
  ipv4.route-table 110 \
  ipv4.routing-rules 'priority 32033 from 192.168.76.2/32 table 110' \
  ipv6.never-default yes ipv6.ignore-auto-dns yes
ip -4 route get 192.168.76.1 from 192.168.76.2
```

После настройки интерфейса дайте NetworkManager закончить применение и проверьте,
что маршрут действительно идёт по Ethernet. Пример подключения с вашим ключом:

```sh
ssh -b 192.168.76.2 -i /путь/к/вашему/приватному_ключу \
  -o IdentitiesOnly=yes -o UserKnownHostsFile=./re-cs-06-known-hosts \
  root@192.168.76.1
```

При первом соединении сверьте ключ по доверенному каналу/записи установочного
процесса; не отвечайте автоматически «yes» неизвестному устройству.

### Что проверить, прежде чем подключать WAN

```sh
ubus call system board
df -h /overlay
cat /sys/block/loop0/loop/backing_file
fw_printenv -n jd_failsafe_counter
uci -q get network.wan.auto
uci -q get network.wan6.auto
iw dev
```

Ожидается установленная версия r9, постоянный ext4 overlay, правильный выбранный
rootfs, счётчик `0`, оба `auto` равны `0`, активных Wi-Fi-интерфейсов пока нет.
Дополнительно установочный инструмент проверяет образ чтением обратно, GPT,
сохранность защищённых разделов и собственные MAC.

Создайте контрольный файл в `/etc`, перезагрузите **по SSH** и проверьте, что файл,
пароль, ключ доступа и host keys сохранились, а счётчик снова `0`. Затем отдельно
проверяется холодное включение. Не называйте установку проверенной только потому,
что один раз открылась веб-страница.

WAN, Wi-Fi и flow offloading по умолчанию отключены намеренно. После приёмки
настройте свой тип интернета, корректную страну, шифрование и пароль Wi-Fi.
Поддержка Wi-Fi 7/MLO этой инструкцией не обещается.

## Если что-то пошло не так

| Симптом | Что сделать сначала |
| --- | --- |
| Сток не открывается | Проверить LAN/WAN, загрузку, адрес шлюза и реальный Ethernet-маршрут |
| API написал ошибку после открытия Telnet | Отдельно проверить порт/вход; код ответа не доказывает, что команда не выполнилась |
| После записи нет SSH | Проверить `192.168.76.1`, IP компьютера и policy route; не начинать с повторной прошивки |
| Линк есть, веб не открывается | Проверить маршрут, SSH и факт загрузки нужной системы; это ещё не «кирпич» |
| Нет линка после нескольких минут | Не циклировать питание и не переписывать U-Boot; нужен разбор журнала, возможно UART |
| Пароль/ключ не подходят | Не делать reset вслепую: проверить, восстановился ли личный архив |
| Установщик сообщил ошибку записи/хеша | Не перезагружать самовольно; сохранить журнал и определить, на каком шаге остановился |

**UART роутера — 1,8 В.** Нельзя подавать 3,3 В TX адаптера напрямую на RX роутера.
Нужен подходящий согласователь уровней; VCC адаптера к роутеру не подключается.
На штатном U-Boot не подтверждено HTTP-recovery, как на модифицированном первом
экземпляре. Зажимание Reset по чужой инструкции не заменяет план восстановления.

Для помощи сообщите модель, версию, этап и **очищенный** текст ошибки. Не публикуйте
пароли, cookie/sessionid, приватные ключи, factory/ART, полный дамп и личные MAC/SN.

## Что уже действительно проверено

- Существующий stock U-Boot запускает исправленную ARM64-систему без замены загрузчика.
- r9 автоматически восстановила личную конфигурацию в 122 МиБ rootfs.
- Вход по SSH, две сетевые перезагрузки, постоянный overlay и неизменность host keys.
- Подключённый LAN: 2,5 Гбит/с; iperf3 — около 2,34 Гбит/с к роутеру и 2,03 Гбит/с
  от роутера, без TCP-повторов в двух 20-секундных тестах.

Это **не** приёмка всех портов, Wi-Fi, холодного старта, восстановления после
отключения питания во время записи или универсального установщика для всех стоков.
